# cpt-spectrum-plan.md — Does CPT itself benefit from Spectrum layer selection?

**Status:** design only. Nothing in this document has been implemented or run. It is written to be
executed autonomously, overnight and into the following day, by someone who has not read the
preceding session's transcript.

**Where this file lives, and why here.** The CPT *code* it specifies goes under
`model-experiments/03-cpt-only/cpt_train/spectrum/`, but the *question* is a third arm of the
`04-cpt-sft` Spectrum probe (`docs/spectrum-plan.md` → `docs/spectrum-workflow.md` →
`docs/reports/2026-08-spectrum-vs-stock-comparison.md`), every downstream stage lives in
`04-cpt-sft/`, and the final write-up is a three-way comparison against two arms that are already

## 0. The question, stated precisely

The existing `sft_cptv2_probe/` arm asked: *given a CPT adapter trained on the stock trailing-16
blocks (32–47), does Spectrum-layer SFT/DPO on top of it help?* Answer (comparison report §1):
no significant lift at any stage. But that arm had to bolt a non-contiguous 16-block LoRA onto a
contiguous 16-block CPT delta, which forced the union-convert-and-freeze machinery
(`sft_cptv2_probe/spectrum/cptv2_spectrum_lora_layers.py`, `merge_frozen_keys.py`): convert the
21-block union `picks ∪ {32..47}`, load CPT-v2 into all 21, freeze the 5 CPT-only blocks, train
16, merge the frozen 5 back into every saved artifact. That is a confound, not just complexity —
report §4 names it as the leading hypothesis for the asymmetry.

**This probe removes the confound.** Re-run CPT from scratch with the LoRA on Spectrum's 16 picks,
then SFT and DPO on the *same* 16 picks. One continuous 16-block LoRA lineage, base → CPT → SFT →
DPO, with no union, no freeze, and no merge step anywhere. Exactly one variable changes versus
CPT-v2: which 16 decoder blocks carry the LoRA.

The frozen Spectrum selection (a property of the base model's weights, already computed and
verified — do **not** recompute it):

```
[0, 22, 23, 27, 30, 34, 36, 37, 38, 39, 41, 42, 43, 44, 45, 47]   # 11/16 overlap with {32..47}
model-experiments/04-cpt-sft/sft_fresh_probe/spectrum/configs/spectrum_layers.json
```

Note `0` is in the picks. That single fact drives three things this plan keeps coming back to:
backprop must traverse all 48 blocks (§6 time budget, §8 OOM risk), `adapter_config_fix.py`'s
rewrite lands on the worst-case `num_layers: 48` (§2.5), and the eval-time silent-drop trap applies
to the CPT stage's own CF-check, which the existing CPT code has never had to handle.

## 2. The CPT-on-Spectrum driver design

### 2.1 `run_cpt_leg_spectrum.py` — the import-order-safe patch

`run_cpt_leg.py:29` is

```python
from mlx_lm.tuner.utils import build_schedule, linear_to_lora_layers, print_trainable_parameters
```

A `from X import Y` **binds `Y` into `run_cpt_leg`'s own module globals at import time**. Setting
`mlx_lm.tuner.utils.linear_to_lora_layers = replacement` after `run_cpt_leg` has been imported does
nothing — `run_cpt_leg.linear_to_lora_layers` still points at the stock function, and line 71 calls
the stock trailing-16 slice while the process *looks* patched. This exact class of bug has already
bitten this project twice (`dpo_spectrum_train.py`'s header documents the
`mlx_lm_lora.utils` case: three rebind sites, not one).

The fix is ordering, made explicit and asserted rather than assumed. `run_cpt_leg_spectrum.py`,
top to bottom, with **no module-level import of `run_cpt_leg` anywhere above the patch**:

```python
#!/usr/bin/env python3
"""CPT leg driver on the Spectrum-picked layers. Identical to run_cpt_leg.py in
every respect except which 16 decoder blocks get LoRA -- it literally CALLS
run_cpt_leg.run_leg(), after rebinding the layer-selection function that
run_cpt_leg's own top-level `from mlx_lm.tuner.utils import ...` will bind."""
import argparse, json, sys
from pathlib import Path

SELF        = Path(__file__).resolve().parent            # .../03-cpt-only/cpt_train/spectrum
CPT_TRAIN   = SELF.parent                                # .../03-cpt-only/cpt_train
REPO_ROOT   = SELF.parents[3]                            # repo root
# NOTE the index: SELF is the spectrum DIRECTORY, so parents[0]=cpt_train,
# [1]=03-cpt-only, [2]=model-experiments, [3]=repo root. In
# run_epoch_loop_spectrum.py below the same expression starts from the FILE
# (Path(__file__).resolve().parents[...]), which shifts every index by one --
# hence parents[4] there and parents[3] here. Assert it rather than trust it:
assert (REPO_ROOT / "models" / "qwen-q4").exists(), f"REPO_ROOT misresolved: {REPO_ROOT}"
FRESH_SPEC  = REPO_ROOT / "model-experiments/04-cpt-sft/sft_fresh_probe/spectrum"
for _p in (str(FRESH_SPEC), str(CPT_TRAIN)):
    if _p not in sys.path:
        sys.path.insert(0, _p)

# ---------------------------------------------------------------- STEP 1
# Parse ONLY --spectrum-layers here. Everything else is forwarded to run_leg().
def _parse():
    ap = argparse.ArgumentParser()
    ap.add_argument("--spectrum-layers",
                    default=str(SELF / "configs" / "spectrum_layers.json"))
    ap.add_argument("--config", required=True)
    ap.add_argument("--adapter-path", required=True)
    ap.add_argument("--iters", type=int, required=True)
    ap.add_argument("--done-steps", type=int, required=True)
    ap.add_argument("--resume-adapter-file", default=None)
    ap.add_argument("--resume-optimizer-file", default=None)
    return ap.parse_args()

# ---------------------------------------------------------------- STEP 2
# Patch BEFORE run_cpt_leg is imported. This assertion is the whole contract.
assert "run_cpt_leg" not in sys.modules, (
    "run_cpt_leg was imported before the layer patch was applied -- its "
    "`from mlx_lm.tuner.utils import linear_to_lora_layers` has already bound "
    "the STOCK trailing-16 function into its own globals and the rebind below "
    "cannot reach it. Do not move any import above this line."
)
from spectrum_lora_layers import (           # noqa: E402  -- ordering is the point
    load_layer_ids, apply_patch, make_linear_to_lora_layers,
    EXPECTED_LORA_TENSORS, EXPECTED_TRAINABLE_PARAMS,
)

args = _parse()
LAYER_IDS = load_layer_ids(args.spectrum_layers)      # sorted, deduped, range-checked
apply_patch(LAYER_IDS)                                 # runs _assert_upstream_still_matches()
                                                       # then rebinds BOTH
                                                       #   mlx_lm.tuner.utils.linear_to_lora_layers
                                                       #   mlx_lm.lora.linear_to_lora_layers

# ---------------------------------------------------------------- STEP 3
import run_cpt_leg                                     # noqa: E402
import mlx_lm.tuner.utils as _tu                       # noqa: E402
assert run_cpt_leg.linear_to_lora_layers is _tu.linear_to_lora_layers, \
    "run_cpt_leg bound a different linear_to_lora_layers than the patched one"
assert getattr(run_cpt_leg.linear_to_lora_layers, "spectrum_layer_ids", None) == LAYER_IDS, \
    "run_cpt_leg is holding the STOCK linear_to_lora_layers -- the patch did not take"
```

`apply_patch` is the fresh arm's, unchanged. It rebinds exactly two attributes and refuses to run
if `mlx_lm_lora` is in `sys.modules` — correct here, since `run_cpt_leg` never imports it. It also
runs `_assert_upstream_still_matches()`, which pins mlx-lm `0.31.3`, the four-parameter signature,
the `for l in model.layers[-max(num_layers, 0):]` marker and the SHA-256
`96aa5d61a790a24b228127f5b5eaf2205a833e636bfa1827ab8f65fbc6ddd111`. Installed today: mlx-lm
0.31.3, mlx-lm-lora 2.1.0, mlx 0.31.2 — the pins hold. If a venv rebuild moves them, the guard
raises at launch instead of training the wrong layers.

`make_linear_to_lora_layers` also asserts `num_layers == len(ids)`, so the config's `num_layers: 16`
and the 16 picks cannot silently disagree.

### 2.2 Pre- and post-conditions the driver adds (lessons 1 and 6)

Three checks, all cheap, all in `run_cpt_leg_spectrum.py`:

**(a) Resume-file key check, before `run_leg` (pure file read, no model load).**
`run_cpt_leg.py:76` does `model.load_weights(args.resume_adapter_file, strict=False)` *after*
conversion; `strict=False` silently drops any key naming a block that was not converted. Within a
single run this can only fail if a checkpoint from a different layer set is passed by mistake — so
assert it:

```python
if args.resume_adapter_file:
    keys = list(mx.load(args.resume_adapter_file).keys())
    blocks = sorted({int(k.split(".")[1]) for k in keys if k.startswith("model.layers.")})
    assert blocks == LAYER_IDS, f"resume file covers blocks {blocks}, picks are {LAYER_IDS}"
    assert len(keys) == EXPECTED_LORA_TENSORS, f"resume file has {len(keys)} keys, expected 256"
```

**(b) Checkpoint post-condition, after `run_leg` returns.** Read back
`{final_it:07d}_adapters.safetensors` and assert: 256 keys; block index set exactly `LAYER_IDS`;
and **no tensor is all-zero**. That last one is lesson 6 — verify weights are genuinely nonzero at
the *first* checkpoint, not after 26 hours:

```python
w = dict(mx.load(str(ckpt)))
mx.eval(list(w.values()))                       # materialize BEFORE inspecting (lesson 1)
zeros = [k for k, v in w.items() if float(mx.max(mx.abs(v))) == 0.0]
assert not zeros, f"{len(zeros)}/{len(w)} checkpoint tensors are all-zero: {zeros[:5]}"
```

Note `lora_b` is initialised to zeros by `mlx_lm/tuner/lora.py`, so this assertion is only
meaningful *after* training has taken at least one optimizer step — which is true at every leg
boundary and at the §3 dry leg's 2 iters. It is not valid on a 0-iter run.

**(c) The MLX in-place-write audit (lesson 1).** `mx.load()` on a safetensors file is a lazy
memory map; writing the same path before the loaded arrays are evaluated truncates the mmap they
are still reading from and silently zeros them — the bug that corrupted the cptv2 arm's SFT
adapter (comparison report §3.1). **Every place in this pipeline that reads a safetensors file:**

| Site | Reads | Writes | Hazard? |
|---|---|---|---|
| `run_cpt_leg.py:39 restore_optimizer_state` | `mx.load(optimizer file)` | never | No — read-only |
| `run_cpt_leg.py:108-109` final save | nothing | `mx.save_safetensors(NEW numbered path)` | No — different path, from live model params |
| §2.2(a) resume-key check | `mx.load(resume file)` | never | No — read-only |
| §2.2(b) checkpoint check | `mx.load(ckpt)` | never | No — read-only, and `mx.eval` first anyway |
| `adapter_config_fix.rewrite_adapter_config` | `adapter_config.json` via `json`/`Path` | same JSON path | No — plain text, no `mlx.core` involved |
| `adapter_config_fix.adapter_keys` | `mx.load(adapters.safetensors)` | never | No |
| `run_epoch_loop.revert_to_previous` | `shutil.copy` (bytes) | `adapters.safetensors` | No — `shutil`, not `mx` |

**There is no read-then-overwrite-in-place site in this pipeline, and no merge step at all** — the
union/freeze design that *needed* `merge_frozen_keys.py` is exactly what this probe eliminates
(§4.4). If the implementer adds any new script that post-processes a safetensors file, the rule is:
call `mx.eval(list(loaded.values()))` before any write, or write to a different path. Encode it in
the new `spectrum/README.md`.

### 2.4 `run_epoch_loop_spectrum.py` — a fork is required, not optional

`run_epoch_loop.py` cannot be reused with different arguments: it has **no arguments**. Every path
is a module-level constant (`ADAPTER_DIR`, `RESULTS_DIR`, `STATE_FILE`, `REVIEWS_FILE`, `MANIFEST`,

### 2.5 The CF-check silent-drop trap — why the rewrite is mandatory per leg

`run_leg_cf_check.py` calls `run_cf_check.run_model(..., adapter_path=adapter_dir)`, which routes
through `mlx_lm.utils.load(..., adapter_path=...)` → `mlx_lm/tuner/utils.py:load_adapters` →
`linear_to_lora_layers(model, config.num_layers, ...)`, reading `num_layers` **out of the adapter's
own `adapter_config.json`** — a fresh, unpatched process that knows nothing about Spectrum.
`run_cpt_leg.py:82` writes that file with `num_layers: 16` via `save_config(vars(args))` at the
start of every leg. So without the rewrite, the CF-check would rebuild LoRA on blocks **32–47**,
then `load_weights(..., strict=False)` would silently drop blocks 0, 22, 23, 27 and 30 — and the
gate would be scoring a partially-loaded model. That is the same failure class as the `mlx_lm.fuse`
bug (2026-07 report §3) and exactly what `adapter_config_fix.py` exists to prevent.

`spectrum_num_layers(picks) = 48 - min(picks) = 48 - 0 = 48`. Because block 0 is picked, the
rewrite lands on the documented worst case: all 48 blocks converted at load time, 32 of them
covered-but-untrained. Those are harmless numerically — `lora_b` is zero-initialised and both
`LoRALinear.__call__` and `LoRASwitchLinear.__call__` compute `y + scale * (x @ a) @ b`, so an
untrained block's delta is identically zero, and `mlx_lm/utils.py` calls `model.eval()` at load so
dropout is inert. They cost memory: 32 × 17.615M ≈ 564M F32 params ≈ **2.25 GB** on top of the
~16 GB q4 base, during CF-check only. That is generation-only (no optimizer, no activations for
backprop), so it fits — but it is *measured* in the §3 dry run, not assumed.

Immediately after the rewrite and before the CF-check, run the mandatory assertion
(`adapter_config_fix.assert_adapter_keys_present`) exactly as `eval_sft_spectrum.sh` does, and
require `n == 256`. It raises; it never warns.

Two consequences worth stating so they are not rediscovered as surprises: (i) the next leg's
`run_cpt_leg.py` overwrites `adapter_config.json` back to `num_layers: 16` — expected, which is why
the rewrite runs *every* leg rather than once; (ii) `run_leg_cf_check.py`'s own docstring contract
still holds — the CF-check must run right after its leg and before the next leg starts, because the
adapter directory is shared and rolling.

### 2.6 Resume and checkpoint semantics — unchanged from CPT-v2

- `run_cpt_leg.py` writes, per leg, `{done_steps+iters:07d}_adapters.safetensors` (trainable params
  only) and `{...:07d}_optimizer.safetensors` (flattened Adam state incl. the global `step`, which
  is what keeps the single 6528-iter cosine schedule continuous across 12 subprocess boundaries).
  `mlx_lm`'s own periodic save is disabled via `steps_per_save = args.iters + 1`.
- `resume_point()` re-derives `(done_steps, resume_adapter_file, resume_optimizer_file)` from the
  highest-numbered checkpoint on disk. **Killing and relaunching `run_epoch_loop_spectrum.py` loses
  at most the in-flight leg.** This is the property that makes a 26–30 h run survivable overnight;
  do not break it.
- Expected checkpoints: `0000544` … `0006528`, 12 of each. Sizes from CPT-v2 (identical shapes,
  since only *which* 16 blocks changed): 1.13 GB per adapter, 2.25 GB per optimizer → **41.7 GB**
  for the full run. 2.8 TiB free on `/Volumes/ExtremePro` today.

### 2.7 Freezing the result before SFT touches it

When the loop ends, `adapters/cpt-v2-spectrum/adapters.safetensors` holds the accepted checkpoint
(`revert_to_previous()` guarantees this even on `halt_keep_previous`). Before starting SFT, copy it
plus a rewritten `adapter_config.json` into `adapters/cpt-v2-spectrum-final/`, and record which
global step it corresponds to in `results/cpt-v2-spectrum/json/training_state.json`'s final entry.
Reasons: (a) the CF-check rewrite leaves `num_layers: 48` in the live dir, and a later stray run of
anything would rewrite it again; (b) §7 wants a CPT-only functional eval of this adapter, which
needs a stable directory; (c) never-delete/never-clobber discipline (lesson 8).

### 4.4 Why the union/freeze machinery is NOT needed here — the checkable argument

The cptv2 arm needed it because of a set-theoretic fact stated in
`sft_cptv2_probe/spectrum/README.md`: its `resume_adapter_file`
(`03-cpt-only/adapters/cpt-v2/adapters.safetensors`) covers exactly blocks 32–47, `mlx_lm.lora`
applies it with `strict=False` **after** conversion, and the picks also have exactly 16 members —
so the picks can never be a superset of {32..47} unless the two sets are identical. A picks-only
conversion would therefore silently drop the 5 CPT-only blocks and train on a base that had lost
part of its CPT delta. Hence: convert the 21-block union, load CPT-v2 into all 21, freeze
`{32..47} \ picks`, and — because `mlx_lm/tuner/trainer.py` saves only `trainable_parameters()` —
merge the 5 frozen blocks back into every artifact (`merge_frozen_keys.py`, which is where the
in-place-`mx.load` corruption bug lived).

In **this** arm the resume file is `cpt-v2-spectrum-final/adapters.safetensors`, whose key set is
**exactly the picks**, asserted three ways:

1. `run_cpt_leg_spectrum.py`'s post-condition asserted it at every CPT leg (§2.2b): 256 keys, block
   indices == picks.
2. The SFT conversion converts exactly the picks (`spectrum_lora_layers.make_linear_to_lora_layers`
   with `num_layers == len(ids) == 16` enforced).
3. Therefore `load_weights(..., strict=False)` has a home for **every** key and drops nothing. Prove
   it rather than argue it: before launching SFT, run the fresh arm's existing
   `--verify-layers` DPO-style key check — or, simpler and sufficient, the plain assertion

   ```
   set(mx.load(cpt_final).keys()) == set(k for k,_ in tree_flatten(model.parameters())
                                          if k in mx.load(cpt_final))
   ```
   via `adapter_config_fix.assert_adapter_keys_present(model, cpt_final)` after
   `load("models/qwen-q4", adapter_path="…/cpt-v2-spectrum-final")` — which is exactly what
   `eval_sft_spectrum.sh` already does, and what the CPT-only eval in §7 will do anyway.

Consequences, each of which is a subsystem that simply does not exist in this arm:

- **No union conversion** → no `cptv2_spectrum_lora_layers.py` equivalent; the fresh arm's shared
  `spectrum_lora_layers.py` is used verbatim.
- **No frozen blocks** → `trainable_parameters()` is all 256 keys, so every file training writes is
  already complete.
- **No merge step** → `merge_frozen_keys.py` is never invoked, so the in-place `mx.load` +
  overwrite hazard that zeroed the cptv2 arm's SFT adapter (comparison report §3.1) **cannot recur
  in this pipeline** (§2.2c audits every remaining read site).
- **No union in the §7 rewrite** → `spectrum_num_layers(picks) = 48`, driven by the picks alone,
  identical to the fresh arm's invocation.
- **~1.9 GB less resident memory during DPO** than the cptv2 arm carried (21 converted blocks vs
  16), which is the exact overhead report §3.2 blamed for that arm's OOM. See §5.3.

### 5.2 `eval_dpo_spectrum.sh`

Copy the fresh arm's; retarget the same variables. Keep the §7 rewrite + `assert_adapter_keys_present`
with `assert n == 256` on both the final and the best adapter, and the two full-holdout evals
(final checkpoint, best snapshot) with the same `LAST_EVAL_STEP`/`BEST_EVAL_STEP` offsets so the
metrics rows stay distinguishable.

### 5.3 Memory — anticipate the mitigation, do not be surprised by it (lesson 3)

DPO holds **both** the policy and the reference model. The cptv2 arm hit
`kIOGPUCommandBufferCallbackErrorOutOfMemory` at the default `DPO_MAXLEN=512` during its 8-iter
dry run, with 37 GB+ of free *system* RAM — this is macOS's GPU wired-memory ceiling
(`iogpu.wired_limit_mb`, system default ≈ 70–75 % of 48 GB), not a RAM shortage. Raising it needs
`sudo sysctl`, which is unavailable here. Report §3.2 attributes the arm-specific margin to its
~1.9 GB union-conversion overhead, which **this arm does not have** (§4.4) — so `DPO_MAXLEN=512`,
the fresh arm's value, is the right thing to attempt first.

Standing instruction:

1. Run the 8-iter dry run at `DPO_MAXLEN=512`. If it completes (fresh arm's peak was well inside
   budget; cptv2's at 384 was 39.8 GB), keep 512 for the real run.
2. If it OOMs, **immediately retry the dry run at `DPO_MAXLEN=384`** — the value that resolved it
   for the cptv2 arm and the same value the script's own OOM ladder uses as its documented last
   resort. Note that the ladder wraps only the *segmented real run*, not the one-shot dry run, which
   is why the dry run does not self-heal.
3. Whatever value the real run uses, **record it in the write-up as a recipe deviation** if it is
   not 512, along with report §3.2's honest caveat that some longer DPO pairs may be truncated.
4. Do not chase it further than 384. If 384 OOMs, stop and report; do not start improvising batch
   or beta changes, which would break the one-variable comparison.

### 6.3 The honest statement about "overnight"

**This will not finish overnight.** The CPT stage alone is ~28–30 hours — roughly 3.5× a literal
8-hour night, and ~1.7× longer than CPT-v2's own 16.4 h because Spectrum's inclusion of block 0
makes every backward pass traverse the full network. Realistically:

- **Night 1 (~8 h unattended):** setup + all gates + roughly legs 1–3 of 12.
- **Day 2:** legs 4–10.
- **Night 2:** legs 11–12 finish, then SFT starts and runs to completion.
- **Day 3:** SFT eval, DPO, DPO eval, write-up.

The loop is resumable by construction (`resume_point()` re-derives from on-disk checkpoints), so
a sleep, a kill, or a crash costs at most the in-flight leg (~2.2 h). Launch each stage with a
single background mechanism, never `&` plus `run_in_background` together (lesson 4), and check in
per leg via `results/cpt-v2-spectrum/json/training_state.json`.

If the calendar genuinely cannot absorb ~40 hours, the *only* honest reductions are:
- Stop CPT at the floor (leg 6, ~14–15 h) — but the run is then **not** recipe-comparable to
  CPT-v2's 12 legs, and the write-up must say so prominently rather than compare the numbers as if
  they matched.
- Skip the DPO stage and report SFT only — the SFT-stage comparison is the primary result anyway
  (§7).

Do not silently shorten the schedule, drop the ceiling, or reduce `max_seq_length` to make the
clock work. Any of those turns a one-variable probe into a two-variable one.

## 7. Final comparison plan

### 7.1 The write-up

`model-experiments/04-cpt-sft/docs/reports/2026-08-cpt-spectrum-three-way.md`, following the
structure of `2026-08-spectrum-vs-stock-comparison.md`: headline table, per-stage detail, incidents,

### 7.2 The statistic

This project's convention, used in both existing comparison reports — **two-proportion z-test**:

```
z = (p1 - p2) / sqrt( p_pool * (1 - p_pool) * (1/n1 + 1/n2) ),    p_pool = (x1 + x2) / (n1 + n2)
```

All n = 855 (the full code-graded holdout). Report Δ in percentage points, z to 3 dp, p to 3 dp
(or `<0.0001`), and a plain Yes/No/Marginal at α = 0.05. McNemar may be reported as a secondary
paired statistic (the two arms score the identical 855 rows), but the z-test is the headline number
so this report is directly comparable to its two predecessors.

State this in the plan so the reading is not chosen after the fact:

## 8. Risks and mitigations

**R1 — Wall clock. Highest-probability problem.** ~28–30 h for CPT, ~37–41 h end to end. The 1.59×
Spectrum slowdown is measured, not guessed, and is a direct consequence of block 0 being picked.
*Mitigation:* §6.3's honest schedule; leg-level resumability; check `training_state.json` per leg;
the only legitimate reductions are stopping at the floor or dropping DPO, and both must be flagged
in the write-up. Never shorten by changing the recipe.

**R2 — OOM during CPT training. Highest-severity problem.** CPT runs at `max_seq_length: 4096`
(vs SFT's 3072) *and* now backprops through all 48 blocks. Activation memory is strictly higher
than both CPT-v2 (same seq length, 16-block backward span) and the fresh spectrum SFT (same
backward span, shorter sequences) — neither of which is a proof it fits. *Mitigation:* the §3 gate-2
dry leg reports `Peak mem` **before** any long run starts; treat a peak within ~2 GB of the ceiling
as a stop. If leg 1 OOMs outright, note plainly that the obvious knob is the wrong one: the corpus
is **packed** into 4096-token windows, so lowering `max_seq_length` truncates every window and
silently changes the dataset — a second variable. `batch_size` is already 1 and `grad_checkpoint`
is already on. If it does not fit at 4096, the honest outcome is "this probe is not runnable at
CPT-v2's recipe on this machine", reported as such, not papered over with a re-pack.

**R3 — CF-check harness is currently broken (`03-new` stale path).** Would hard-fail at leg 1's
gate, ~2.2 h in. *Mitigation:* §1.3 fix + §3 gate 3, which runs the whole CF path end to end on a
throwaway adapter before the real run starts.

**R4 — CF-check overwriting CPT-v2's `cf_check_*.json`.** `_save_full_results` hardcodes
`results/cpt-v2/json/` and the new run's step numbers are *identical* (544 … 6528), so CPT-v2's
per-leg CF evidence would be silently destroyed. Precious, single-copy, irreplaceable.
*Mitigation:* §1.3's `JAC_CF_RESULTS_DIR` env var; §3 gate 3 asserts the file lands in the new dir
and not the old one. This is lesson 8 applied to something that is not obviously a "model".

**R5 — Silent partial adapter load at CF-check / eval time.** `load_adapters` reads `num_layers`
from `adapter_config.json` (written as 16 by every leg) and rebuilds LoRA on 32–47;
`load_weights(strict=False)` then drops blocks 0/22/23/27/30 without a word. The CF-check would
score a partially-loaded model and could trip the gate into a spurious `halt_keep_previous`.
*Mitigation:* `adapter_config_fix.py` rewrite (→ `num_layers: 48`) **plus**
`assert_adapter_keys_present` (must return 256) before **every** CF-check and every eval, as an
enforced step in `run_epoch_loop_spectrum.py`'s loop, not a manual habit.

**R6 — MoE layer-index handling in a new context.** `spectrum_lora_layers.py`'s verbatim
`to_lora` dispatch, including the `SwitchLinear`/`QuantizedSwitchLinear` → `LoRASwitchLinear`
branch (6 of the 8 LoRA tensors per block are stacked expert projections), is already verified —
but only for the SFT/DPO paths and never for `run_cpt_leg`'s call site, and never with CPT's
`max_seq_length: 4096`. *Mitigation:* §3 gate 1's `--verify-layers` asserts 48 `LoRASwitchLinear`
instances (3/layer × 16), all 8 suffixes per picked block, 256 tensors, and trainable ==
281,837,568 exactly, with the stock control confirming the count is placement-invariant; §3 gate 2
independently confirms the `0.923% (281.838M/30532.123M)` banner from a real training process.

**R7 — Import-order regression.** Any future edit that hoists `import run_cpt_leg` above the patch
silently reverts the whole probe to trailing-16 while every log line still says "spectrum".
*Mitigation:* the `assert "run_cpt_leg" not in sys.modules` guard, the two post-import identity
assertions, the unit tests in §2.8, and the checkpoint post-condition in §2.2(b) — four independent
detectors, the last of which catches it even if the first three are deleted.

**R8 — MLX lazy-mmap zeroing (lesson 1).** The bug that silently zeroed the cptv2 arm's SFT
adapter. *Mitigation:* structural — this pipeline has **no merge step and no read-then-overwrite
site** (§2.2c audits all seven safetensors touch points); plus `mx.eval()` before inspection in the
post-condition, plus the first-checkpoint nonzero assertion (lesson 6) so corruption surfaces after
2 iters rather than after 26 hours. The rule for any new script is written into
`spectrum/README.md`.

**R9 — DPO OOM.** Anticipated, not a surprise: §5.3's two-step plan (try 512, fall back to 384,
stop there and report), plus the script's own OOM ladder for the segmented run. This arm carries
~1.9 GB less than the cptv2 arm that actually hit it.

**R10 — CF-check regression halting the run.** The floor of 6 protects legs 1–6 unconditionally; a
single non-16/16 at leg ≥ 7 halts and keeps leg N−1. Given block 0's proximity to the embedding,
this is a *plausible real outcome*, not just a failure mode. *Mitigation:* keep the gate exactly as
it is — detecting this is the point (lesson 9). Persist full per-task CF output every leg
(`cf_check_{step}.json` + `logs/cf{N}.log`) so a halt is diagnosable, and report a halt as a
finding ("Spectrum CPT triggered the CF stop-loss at leg N; CPT-v2 never did"), not as a run
failure. A halted run still yields a usable adapter for the SFT/DPO stages, at fewer legs — say so.

**R11 — Disk.** CPT 41.7 GB (12 × 3.38 GB) + SFT checkpoints ~11.3 GB (10 × 1.13 GB) + DPO
snapshots ~14.7 GB (13 × 1.13 GB) + final snapshots ≈ **70 GB**. 2.8 TiB free today. *Mitigation:*
`df -h /Volumes/ExtremePro` before launch and re-check at leg 6; never delete a checkpoint to make
room — archive or stop.

**R12 — Accidentally staging a >100 MB file.** Cost hours of git-history recovery before.
*Mitigation:* §1.4 — verify the `.gitignore` globs with `git check-ignore -v` (do not assume the
`**/adapters/` and `*_probe/results/*/snapshots/` rules match the new names), and run the
`find -size +50M` sweep over staged files before every commit.

**R13 — Base-model / selection provenance drift.** `spectrum_layers.json` records
`source_snapshot: b2cff646eb4bb1d68355c01b18ae02e7cf42d120` and
`spectrum_rev: self-implemented:snr_scan.py`. The picks are reused as-is, deliberately (they are a
property of the base weights, shared by every arm). *Mitigation:* the symlinks in §1.1/§1.2 make a
divergent copy impossible; `_assert_upstream_still_matches()` catches an mlx-lm change; the write-up
must state that the selection was reused and **not** recomputed for this arm.
